## 1. 08-14:在自己的两台小机器上先把路走通

**要做什么**:MOSAIC 是一个给 MoE 训练用的 alltoallv 通信库(alltoallv =
每张卡给每张卡发一份大小不同的数据,像 16 个人互相寄快递)。要证明它好,
必须和两个对手 —— NCCL(NVIDIA 官方)和 FAST(论文方案)—— 在**完全相同
的考场**里比:同一份数据、同一把秒表、同一套训练代码。

**这一天干的活**:

- **把 FAST 官方代码接进测试台**。第一跤:官方代码是给 AMD 的 hipcc 编译器
  写的,普通 g++ 编不过(坑 #12,hipcc 会偷偷预包含一个头文件);第二跤:
  改 Makefile 时不小心把默认编译目标换掉了(坑 #13)。
- **接上 RDMA 数据面**(RDMA = 网卡直接读写内存,不用 CPU 帮忙搬)。
  这里踩了一个教科书级的坑 #14:为了验证数据没搬错,给每一片数据算
  校验码(CRC),结果速度从 88Gbps 掉到 1.8Gbps —— 慢了 48 倍!
  **取舍**:逐片 CRC 默认关掉,正确性改用"端到端校验"—— 收完之后整体
  对一次答案。平时不付钱,要 debug 时再打开。
- **写 mosaic_torch**:让训练代码一行不改就能换通信后端(只替换
  Megatron 里 all_to_all 那一个函数指针)。坑 #19:双机测试时环境变量
  不会自动传到另一台机器、上一次跑挂的僵尸进程还占着端口 —— 这两个
  "隐形杀手"后来写进了所有启动脚本。

**一个重要的设计取舍(D1)**:MOSAIC 的"大脑"(协议决策)只用**一个
CPU 线程**跑事件循环。为什么不用多线程?因为单线程 = 没有锁 = 每次跑
决策顺序完全一样 = 可以和模拟器逐字对答案(replay_core_test 至今保持
0 分歧)。代价是这个线程忙不过来时没有帮手 —— 后面第 4 章会专门验证
它够不够用(结论:够)。

## 2. 08-15 白天:第一次上超算 Raven,连摔四跤

Raven 是德国 MPCDF 的超算:192 台机器,每台 4 张 A100,4 张卡**共享一根**
200Gbps 的 InfiniBand 网线(这个"共享"后面会变成全剧最重要的伏笔)。

**环境搭建就有 9 个坑(R1-R9)**,挑三个有代表性的:

- **R6**:编译 FAST 时明明指定了 A100 架构,还是报错。查下来是 torch 的
  编译脚本会"探测本机有什么 GPU"来决定编译目标 —— 登录节点**没有 GPU**,
  探测失败就回退到"全架构列表",里面混着老掉牙的 sm_50,而新代码在
  sm_50 上根本编不过。修法:显式设 `TORCH_CUDA_ARCH_LIST=8.0`。
  教训:**编译产物不该取决于"编译那台机器上插了什么卡"**。
- **R8**:同步脚本会把本机(L40S 卡,sm_89)编的库**悄悄覆盖** Raven 上
  (A100,sm_80)的版本 —— 不报错,只是跑不动或跑错。修法:同步时排除
  这类产物,远端自己重编。
- **R9**:判卷程序有"假绿"—— 一行结果都没有却报 PASS。修法:零结果
  必须算 FAIL。**假绿比失败危险得多,它会让错误数字进对比表。**

**然后是著名的四连败**(第一次真正跑 16 卡):

1. **R10**:所有 rank 报"连不上 rank 0"。查:引导代码用 `inet_pton` 解析
   地址,它**只认 IP 数字不认主机名**,喂主机名得到 0.0.0.0。本机一直传
   IP 所以从没暴露。
2. **R12**:修完 R10,16 个 rank 全都往第一台机器连。这个坑很阴:环境变量
   `MOSAIC_HOSTS` 的值是"IP1,IP2,IP3,IP4"(带逗号),而 srun 的
   `--export=A,B,C` 语法**按逗号切列表** —— 值里的逗号把列表切碎了,
   每个进程只收到第一个 IP。debug 难点:日志里记的是提交时的完整值,
   看不出子进程实际收到的是半截。教训:**含逗号的值永远别走 --export**。
3. **R11**:单节点"跑通"的 4 个 rank 其实**全挤在 GPU 0 上**(代码里
   写死了 `cudaSetDevice(0)`,本机每台只有 1 张卡所以从没暴露)。
   修法要注意回退:选卡公式 `(rank % G) % 可见卡数` —— 本机 1 张卡跑
   4-rank 冒烟时,裸 `rank % G` 会选出不存在的卡(第一版就犯了,
   本机回归当场抓住)。
4. **R13**:建链全通了,但 dev≠0 的 12 个 rank 疯狂报 event 错误。
   根因非常隐蔽:`cudaSetDevice` 是**每线程**属性 —— 主线程选了卡,
   事件循环线程没选,默认用 dev0。"只有 dev≠0 的 rank 出错"这个分布
   本身就是签名。

**当天下午用第一个占位作业(29344486)又拆了两颗雷**:

- **R14**:一部分 rank 的 QP(网络连接)建不起来。查:每台机器有
  mlx5_0/1/2 三个网络口,其中一个是**以太网管理口**,轮流分配时有人
  分到了以太口。修法:运行时读 `link_layer` 现场挑 IB 口 ——
  后来发现不同机器口的布局还不一样(R21),**静态名单必炸,必须现探**。
- **R15(最精彩的 debug)**:全员几乎收齐,但每个 rank 差最后一小截,
  整个系统卡死。怎么查?**对账单流**:把发送端 trace 里所有"寄出"的
  包裹号,减去接收端所有"签收"的包裹号,剩下的就是丢的那一片
  (src=12→dst=0,offset=608256,73728 字节);再在全网 16 份 trace 里
  搜这一片 —— 只有寄出、没有签收 = 死在管道里。根因:接收环允许
  **乱序消费**,导致"已消费"计数虚高,发送端以为最老的槽空了就复用,
  把还没消费的数据**覆盖**了。修法:接收端严格按序消费。
  这个"槽位复用 + 计数虚高 = 覆盖丢数据"的模式后来又出现过一次。

四连败修完当晚,**4 节点 16 卡三方案全通**(29344486-180906),
MoE 训练也跑通并拿到第一个铁证:**同一作业里 nccl 和 mosaic 的 loss
逐位相同**(29345490)—— 从此"loss 整列 md5 一致"成为每次实验的
正确性门票。

## 3. 08-15 深夜~08-16:旋钮大扫描(T5)

系统跑通了,但慢。这一阶段的方法论叫**探针 cell 法**:选三个代表性
负载当"探针"(小包 hotdst 512K 测起步费、uniform 8M 测吞吐、
hotdst 8M 测热点),**一次只动一个旋钮**,立刻看三个探针的反应。

关键发现(占位 29346066,一晚上 108 步):

- **波数(W)的作用**:MOSAIC 把一次通信切成 W 个"波次"分批发。
  `WAVES=2` 让小包地板从 29.7ms 砍到 15.7ms —— 每多一波要多付一轮
  同步/广播,小包付不起。
- **"知情档"的诞生**:原来代码里有个限速器(模拟器遗留),按额定带宽
  勒住发送。用户定下"**真机为准**"原则:真机永不限速,额定值只喂给
  决策层当参考(`THROTTLE=0`)。限速器从此退役成计数器。
- **解剖对手学到一招**:三方案共用执行底座,所以 trace 格式相同,可以
  直接对比。给 FAST 在热点负载下画"入流路径直方图",发现它 2/3 的字节
  走**两跳**(邻居网卡代收 + NVLink 递进),而 MOSAIC 一半流量在走
  **三跳**的 SPREAD 走廊 —— 每字节多付一整跳。一刀 `CORRIDORS=3`
  (剪掉 SPREAD):hotdst 8M 从 151.7ms 到 **96.0ms,反超 FAST 15%**。
- **定数**(双方各 5 次取中位):四个对照格 MOSAIC 全胜 FAST
  (hotdst 8M +16%、persrc 512K +42%)。
- **但也发现了坏消息**:没有万能配置 —— 帮小包的 W2 会害深中转
  (96→143.7ms)。这个"配置随负载形态变"的矛盾,就是后来
  **在线自适应**思想的起点。

## 4. 08-16:控制面提速 + 找到真正的瓶颈

**控制面**(rank 之间交换"我要发多少/怎么发"的小消息)当时走内核 TCP,
一趟 35µs。探测代替猜测:

- 想上 DPDK(用户态网络,最快)。只读探测(29348215)判死刑:平台
  hugepages 池为 0 且没有 root 权限,固件拒绝建对象 —— **此路平台锁死**
  (细节在 File/platform-limits-0821.md)。
- 改用 eRPC over InfiniBand:四路对照实测(29348237-ctrl)
  kernel TCP 35µs / verbs 单向 SEND 3.0µs / eRPC 可靠 RPC 2.7µs。
  最终**默认档 = verbs SEND**(单向、最便宜),eRPC 留作没有 RDMA 卡的
  机器的兼容档。

**坑 #25 —— 本阶段最大的性能胜利,debug 过程值得细讲**:

MoE 训练里 mosaic 的 a2a 比 NCCL 慢 2.6 倍,但微基准没这么慢。查:

1. 先给每次通信装"相位秒表"(PHASE 仪表)—— 结果发现秒表本身有 bug:
   `notice`(事件线程察觉提交的时刻)**从来没被写入**,恒为 -1。
   先修表,再量。
2. 修完发现 MoE 里察觉延迟 p50 高达 1.66ms(微基准只有 24µs)。
   给事件循环每一段单独计时(evmax),锁定在 `net_poll` 这一段:
   单次要 2.77ms。
3. 看代码:轮询镜像每一圈要发 **1024 个单独的小 cudaMemcpyAsync**
   (每个槽头一个)。torch 满载时每次 launch 要 ~2.7µs——
   1024 × 2.7µs ≈ 2.8ms,数字对上了。
4. 修法:1024 个小拷贝合成一次 `cudaMemcpy2DAsync`。
   效果:**iter 495→331ms(-33%),a2a 砍 45%**(29349040-091635)。

教训:**先修仪表,再信仪表;归因要一路追到"数字对得上"为止。**

**里程碑归因实验(29356303-214419)**:同一作业里 nccl+mosaic 对拍,
把"差距在哪"彻底问清楚:

- `opt` 段(纯计算,不含 a2a)两边只差 0.5ms ⇒ "MOSAIC 的 CPU 线程
  抢了训练的 CPU"这个流行解释**出局**;
- PHASE 分解:协议启动只占 13.4%,**传输占 86.6%** ⇒ 把协议开销砍到零
  也赢不了;
- 换算线速:NCCL 86%、mosaic 43%、而**没有任何调度的 direct 也只有 40%**
  ⇒ 天花板是三方案**共用的数据搬运层**,不是调度层。
  MOSAIC 的调度反而是加分项(43% > 40%)。

这个结论把主战场从"调度层"转到了"数据面"—— 引出第 7、8 章的重建。

## 5. 08-16:一场失败的大战役 —— 异步档(废案)

**动机**:当时每次通信 CPU 都要等 GPU 收尾,想做"异步档":提交完立刻
返回,GPU 自己当搬运工(方案 N:GPU 消费者内核),多次通信在天上飞。

**结局:废案。** 连踩 20 多个坑(#26-#47)后判定:这套设计破坏了一个
隐含前提 —— "每次 collective 是一次隐式的全局同步"。前提一破,
冒出一整类"跨代错误"。挑最有教育意义的几个:

- **坑 #36(头号发现,debug 一击定音)**:全进程随机永久卡死。写了个
  最小探针 `test_persist_sync`:常驻 GPU 内核在场时,把十个 CUDA API
  挨个试一遍 —— **唯独 `cudaFree` 挂死**,其他九个都好好的。而 torch
  的内存分配器随时会 free ⇒ 常驻核必死。修:内核改"有界生命期"
  (每次通信起一个、用完就退),配"代际号"防止上一代残留内核抢活。
- **坑 #45**:给 torch 的缓冲区注册 RDMA 后,torch 的分配器会回收/重映射
  这块内存 ⇒ 网卡按旧地址写 ⇒ `local protection error` ⇒ 连锁崩溃。
  教训:**别人管理的内存不能长期注册**。
- **坑 #46**:抢在对方"进入本次通信"之前把数据发过去,数据落进了
  对方**上一次通信**的缓冲区,还被上一次的计数吃掉 —— 收到的恰好
  是一半。修:发送要等对方的 demand 行到达(= 对方已就位)。
- **坑 #47(最危险)**:一次"异步档跑通了,还快 8 倍!"的假喜报 ——
  查下来结果文件是**本机跑的旧 CSV 被同步脚本推上了超算**,远端跑挂了
  没写新文件,判卷程序把旧文件当成绩单。破绽:要求跑 6 轮却有 10 轮
  数据。修法:同步排除结果文件 + 跑前先删旧文件。
  通则:**判据读的文件,必须只可能由本次运行产生;好得不像话的数字,
  先查它是不是这次跑出来的。**
- **坑 #48(集大成)**:前面六个坑的共同根因 —— **数据头里没有"代际号"**。
  接收方物理上分不清"上一代迟到的包"和"下一代早到的包"。
  修法很便宜:数据头 64 字节里只用了 34 字节,把 `coll` 编号塞进去
  **零额外带宽**,"代际随数据走"。

**废案留下的遗产**(这是取舍的关键):异步档整体删除,但
①**kdesc 消费者内核机制**留下来了(后来成为 gated 档的搬运工);
②**代际号进了线格式**(今天还在);③异步语义后来以轻量得多的
"**一代在飞**"方式实现(第 7 章)—— 只允许一次通信在天上,下一次提交
先收尾上一次,结构上消灭了所有跨代问题。
**教训**:NCCL 的 proxy 模型(CPU 代理收尾)是经过千锤百炼的稳态;
想绕开它,先数数自己准备好踩几十个坑没有。

## 6. 08-17:两个"此路不通"的判决

- **网络虚拟化判死刑(R22)**:曾想把一根 200G 网线逻辑切成 4 条 rail
  来研究多轨调度。实测(29357584):rail 模式让 mosaic 慢 30.7%,而
  **同一步里 NCCL 的时间纹丝不动**(814.5→813.9µs)—— 因为虚拟化只是
  我们自己代码里的规则,勒不住 NCCL。拿它做对比 = 我们绕路、对手走
  直线,不公平。加上用户态没有任何手段真隔离一根物理网卡(要 root)。
  **判决:放弃虚拟化,一切对比在真实拓扑上做**(后来写进铁律)。
- **交换机什么都看不见**(RUNTIME_OBSERVABILITY 调查):计算节点上
  IB 诊断工具全没有,SMP 查询被拒;网卡计数器能读,但一次要 76-115µs
  (事件循环节拍才 100µs,读一个计数器吃掉一整拍)。
  **推论(因祸得福)**:拥塞感知只能靠**端侧自测**(数据什么时候到、
  completion 什么节奏)—— 这恰好就是 MOSAIC "分布式交换视图"的设计,
  中心化问交换机的路线在这个平台上物理不可行。
- 顺手解决三方公平对比的最后死结:FAST 的负载是它源码内部 rand() 生成的,
  我们不能改它源码 —— 反过来**逐字节复刻**它的随机数序列
  (`--mode flashuniform`),交叉验证矩阵逐字节相同。还发现官方数组名叫
  `workload_in_bytes` 但存的其实是**元素个数**,少乘 8 就差 8 倍。

<a name="ch7"></a>
## 7. 08-18~08-19:大扫除与数据面重建(本机)

第 4 章证明瓶颈在数据面,这两天在本机(两台 L40S,100GbE RoCE)动手术。

**先推翻自己的旧理论(local-0819-operator-overhead)**:台账里记着
"小消息只有 36% 线速,因为 1MiB 切片太大、每对只有 1 片、片内没有流水"。
重跑并做切片扫描:把切片改小到 128K/64K/32K,时间**反而单调变差**
(1031/983/1157µs)—— 旧机理**证伪**。真凶是**与字节无关的每次通信
起步费**:发 4KB 的空跑也要 668µs,而且随 rank 数涨(n=2/4/6/8 →
36/247/557/668µs)= 延迟受限,不是带宽受限。
**这就是为什么台账规定"重跑旧实验必须回填引用"** —— 错误结论曾指导过
一轮优化方向,必须让后人看见"结论是怎么变的"。

**大扫除**:60 个环境开关分类,删掉败者(异步档全家、TCP 数据面、
限速器、`MOSAIC_USE_GPU` 改自动探测……),每删一步跑全量回归。
最后剩 25 个旋钮,且**没有一个能改变数据面走法**(单版本纪律)。

**数据面重建三连**:

1. **GDR 探针**(local-0819-gdr-bw):dmabuf 注册后网卡直读显存 91.4Gbps
   = 线速 ⇒ payload 可以完全不过 host 内存。
2. **verbs 面重构**:每片数据 = 双 SGE 一次发出 [64 字节 host 头 |
   GPU payload];控制面独立 QP。效果:256K 消息 53.6µs vs NCCL 115.4
   (**2.2× 反超**),16M 达 85.6% 线速。
3. **流序完成(gated,"一代在飞")**:提交即返回,门内核在调用方的
   CUDA 流上自旋等 `done_flag`,下一次提交先收尾上一次。
   这里有个精彩的竞态 debug:第一版把"输入就绪"的检查放在 CPU 侧,
   60 iter 训练 loss 漂了 6.2e-3 —— 因为交付拷贝和 torch 分配器复用同一
   块内存上的旧 kernel 赛跑。修法:**输入门下沉进消费者内核**(kernel
   入口自旋等输入事件),loss 恢复逐位一致。
   还做了平台探针(local-0819-gate-probe)厘清边界:门内核挂着**不会**
   楔死其他流(推翻旧结论),但并发 `cudaFree` **会**楔死引擎的流调用
   ⇒ 确立铁律 **G.1:门未决窗口内引擎零 CUDA 调用**。

端到端差距:+18.4% → **+8.2%**(本机口径)。

## 8. 08-19 晚~08-20:数据面上 Raven,撞上两堵物理墙

**先在单节点(gpudev 快测档)把机内腿磨快**:消费者内核 v2(按 channel
并行)1438→740µs;轮询解耦 740→609;**dev-pipe2 机内直写**(发送方经
CUDA IPC 直接写进接收方的 recvbuf,1-copy)609→364.6µs —— 机内差距从
9.7× 收到 2.1×。设计要点:接收方"input 就绪后才发布窗口(RWIN)",
发送方绝不猜 —— 猜就是竞态。

**跨机腿撞墙(raven-0819-verbs-plane,写探针逐项测)**:

- **墙一:GDR 读被钉在 121Gbps**(host 读 197 满线速)。网卡读显存要过
  PCIe host-bridge 的 P2P 通路,这是 A100 平台的硬上限,和 NUMA 无关。
- **墙二:GDR 写双稳态**。单向满速,**双向持续流**下随机塌到 22-31Gbps。
  debug 靠计数器:塌陷时发送端 `port_xmit_wait`(有数据但拿不到链路
  credit 的计数)一次涨 2.18 亿,而 RNR/重传/缓冲耗尽全是零 ⇒
  收端网卡往显存排水随机滞流 → 链路层 credit 反压 → 发端被饿死。
  还列了 6 条被逐一证伪的假设(相位偏移/多进程/扇出……),唯一共通项
  = 双向 + 收端落显存。
- **取舍:双侧 host-bounce**(收发都经 host 内存中转,NCCL 同款)。
  多付一次内存拷贝,换稳定满线速。2 节点差距收到 NCCL 的 **+2~4%**。

**一次死锁确立铁律边界**:重构时让事件线程用拷贝引擎(CE)发起拷贝,
MoE 一跑,一台机器的 4 个 rank **连 watchdog 都冻死**(事件线程本身死了)
—— `cudaMemcpyAsync` 在 app 线程持有驱动锁(torch sync)时同样致死。
回退成消费者内核搬运。G.1 从"别调 cudaFree"升级为
"**门未决窗口内一次 CUDA 调用都不能有**"。

**Gate 收敛(单版本纪律的执行)**:nvshmem 数据面 vs verbs 面正面对决,
verbs 全面胜(8M 快 2.2×)⇒ **删掉 nvshmem 数据面**、删 `MOSAIC_NIC`
开关、删 hot-first 发送序(24 格 A/B 全是噪声)。
删的时候还出了**拼接事故**:按文本行区间删,误切掉 kind=6(机内直写
收编)分支 —— bench 和本机回归都覆盖不到这个分支,只有 Raven 的 gated
MoE 能踩出 SIGSEGV。教训:**删代码按语义单位(整个分支/函数)删,
不按行号删**;还要知道自己的回归有哪些盲区。

**口径事故**:第一版宣布"和 NCCL 打平",自查发现拿的是"单 rank 自己的
完成时刻",而 NCCL 的数是"全局 makespan"—— **不同尺**。更正后是
+2~4%。从此对比表必须写明口径(rank0 / makespan / 开门时刻)。

## 9. 08-20 晚~08-21 凌晨:4 节点 16 卡通宵会战

从这里开始是正式形态:4 节点 × 4 卡 = 16 rank(铁律形态)。
起点:MoE 比 NCCL 慢 **+31.4%**。一夜下来压到 +11.7%。

- **先装表再分析**:反向传播的 a2a 原来完全没有仪表(计时器装在
  dispatcher 层,反向绕过它)。下沉到最底层 `all_to_all_single` 后
  发现:**NCCL 自己的反向 a2a 也比前向贵 1.54×** —— 之前把"反向贵"
  全算在自己头上是冤枉。
- **KCONS 消融**:消费者内核用几个 block?扫出来 4×4 形态冠军是 4
  (本机标定的 8 在 A100 上偏大,16 更是灾难 —— SM 抢占把反向 a2a
  拉到 179.9ms)。一个旋钮就把差距 +31%→+14.4%。
  顺带发现非法组合(blocks < channels)会让内核踩非法内存(坑 #56),
  修成 clamp。**容量旋钮的非法组合必须 clamp,不许崩。**
- **gated bench 上线,立刻双杀两个正确性 bug**:让 C++ 基准走和训练
  完全相同的 gated 代码路径(之前不同路径,bug 藏了很久):
  - **坑 #54**:机内直写的偏移语义 —— 邮箱里发布的是"**写入者自己**
    那段的偏移",中转片(替别人搬的数据)直写就落错段:数据腐蚀 +
    记账错乱(机内源多收 1.5 倍、跨机源饿死)。修:直写只许 hop0
    (自己的数据);中转终跳走环路径。
  - **坑 #55**:中转义务不在完成判据里 —— 中转 rank 自己收齐就下班,
    迟到的中转片没人搬。修:**承诺位** —— 每个接收方提前一个字节声明
    "我这次可能走非直发",完成时只等承诺过的人;没承诺的强制直发。
    uniform 负载下全员承诺 0 = 零额外耦合。
- **NIC 物理单元记账(伏笔回收)**:Raven 每节点 4 卡共享一根 HDR200,
  而账本一直把它当 4 根独立管子 —— 分流量时把一根管当四根用,这是
  走廊在 8M uniform 慢 5.4× 的根因。修:运行时探测"谁和谁共享同一块
  物理网卡"(同机 SHM 共识 + 跨机交换设备指纹),账记在 leader 位上。
  **换机器零改动** —— 每卡私有网卡的平台探测出来就是恒等映射。
- **给对手做 CT 扫描(R6)**:离线用同一份 demand 矩阵算出每个倾斜度
  α 下"热节点必须收多少字节 ÷ 线速"= 物理地板。对照实测:NCCL 在
  α1/α2 的 makespan = 地板的 1.03-1.04 倍 —— **NCCL 已经贴地,
  makespan 维度没有超越空间**。目标重构:①斜格追平地板(消掉自己的
  3.5-4× 税);②真正的差异化 = **每个 rank 的完成时间结构**(冷 rank
  早点拿到数据早点开算 —— NCCL 做不到,它的完成还含发送排空)。
- **"到达即计"的反例(重要的负结果)**:波推进按"交付完成"计数而
  不是"数据到达"计数,看起来多了一拍延迟。改成到达即计 —— uniform
  没变化,**斜格反而劣化 27-31%**。原因:交付滞后天然携带"接收端
  排水能力"的信息,是对热点的**保护性背压**。回滚。
  这是"运行时动态调整"哲学的一个漂亮注脚:**别把反馈环里的延迟
  当成 bug,它可能是信息。**
- **W>1 为什么慢 5 倍?三个候选全被 A/B 证伪**(kdesc 切分/TX 让路/
  触发阈值),最后 per-pair 时间线 + 并发微基准锁定真凶:
  **host-bounce 自干扰** —— 网卡满载时,GPU 往 pinned 内存的拷贝速度
  **减半**(20.3→10.3GB/s,每字节过 PCIe 两次的结构成本),波状突发
  节奏把它放大成 3-5×。顺带试了 GDR-read 直发想绕开 —— 被 121G 根桥墙
  反杀(8M uniform 18.2→31.5ms),回退,负结果入账。
- **recv-即-开门**:torch 语义下,门只需要 recvbuf 就绪就能开
  (sendbuf 由 python 引用持有到下一次调用,残余发送后台排空)。
  效果:α2 冷 rank 完成 25-34ms vs NCCL 54-57ms(快 1.6-2.3×)。
- **坑 #57(测谎仪自己说谎)**:α2 某档跑出 26.5ms —— **低于物理地板
  53.6ms,必是假的**。查:一个 rank 的 QP 静默死了,其余 15 个照常
  返回漂亮数字。修:基准内建端到端指纹校验 + 数 rank 行数。
  **口诀:低于地板的数字必是假的,先查校验。**
- **W 在线自适应(R13)**:W 地形非单调还有共振(α1:W2=20ms、W3=56、
  W4=29、W6=108)⇒ 静态公式没救。但 MoE 每个 iter 重复同形状 24 次,
  在线搜索的样本白送 ⇒ 按 demand 形状签名记 EMA、向下探测、劣化档
  进黑名单绕开。α1 makespan 39.8(NCCL 38.5-42.4)追平。
- **α2 悬崖(坑 #58,当时的收尾)**:W≤3 时 QP 级联死(E1025)。
  一整晚三层假设(每波体积/重试包频/交换机缓冲)全被计数器否决:
  失败现场热节点 `port_xmit_wait` 从 0 涨到 704 万,而 RNR 只 +267 ⇒
  真相 = 热节点网卡/host 通路**排水滞流** → 链路层 credit 级联 →
  热节点自己的发送(数据+ACK)被饿死 → 重试耗尽。发送端字节帽
  (24/8/1MB 全试)统统无效 —— **瓶颈在收端排水,发送端限流够不着**。
  当晚只能收编:W 安全下界钳在 6,α2 = 280.6ms(落后 4.4×),
  在台账里写明"调参无解,要改协议"。

当天进表:MoE **+10.8%**(29429498)、A2A 五格(29433075):uniform
打平、α1 胜、α2 落后 4.4× —— 最后一座大山留给下一章。

<a name="ch10"></a>
## 10. 08-21 下午~晚:最后一座大山 —— α2 悬崖与信用反压

**先查外部,不闭门造车**:下载精读 UCCL(arXiv:2504.17307,笔记
Doc/uccl_transport_notes.md)。它的 §4.2 正是我们的病:MoE 的 incast
(很多发送方同时往一个接收方灌)要用 **receiver-driven CC** ——
接收端发 credit 决定谁能发多少,从源头钳住进水速率。NCCL 不死也是
同一本质:每对 ~4MB 的槽环,发送方拿到"槽空了"的信号才发。

**设计取舍(File/design-credit-backpressure-0821.md)**:

1. **采纳"credit 只能由排水事件铸造"**(自时钟):接收端每真正交付
   一片(rx_retire),才发一个 credit。稳态下进水速率自动 = 排水速率。
2. **拒绝 EQDS 的固定速率 pacer**:它假设瓶颈是线速(固定值);
   我们的瓶颈是 host 排水路,速度随负载浮动 —— 拿额定值当真是
   本项目反复踩过的坑("真机为准")。
3. **超越 NCCL 的点**:NCCL 的 credit 是"死"的(固定槽数、每对独立、
   对负载一无所知)。MOSAIC 手里有 NCCL 没有的东西 —— **demand 矩阵**
   (通信开始就知道谁要往谁灌多少)⇒ 初始突发窗可以按目的列热度
   **提前钳住**(W0):uniform 给全窗(行为逐字节不变),热列只给
   2 片/对的起步额度。闭环管稳态,W0 管开局。
4. **协议细节**:credit 用**累计计数器**(报文带绝对值、收端取 max)
   —— verbs 和 TCP 两条通路混跑、乱序、重复都安全;回流搭现成的
   控制面 QP(单程 ~5µs),每圈事件循环合批。

**实现与验证**(commit d4fd8aa):本机回归 20/20 + n=8 hotdst 压测后
上 Raven(占位 29438267):

- **V1:α2 W=1 直发 —— 活了!** makespan **59.5ms**(NCCL 64.0,
  物理地板 53.6),冷 rank 7.7-34ms,零 E1025。原来必死的档位直接反超。
- **V2:uniform 三尺寸零回退**(信用在 uniform 下永不触发限制 ——
  8 片数据 < 32 片的窗)。
- **V3:α1 W=1 边缘随机死 —— 一次教科书式 debug**:
  1. 第一跑 FAIL(r0 E1025),第二跑 PASS —— 悬崖边缘的随机死。
  2. 日志里 E1025 连"对谁发送失败"都没打 ⇒ 先补诊断(从失败 WR 的
     数据头解码出 src→dst),这是永久性的观测改进。
  3. **离线复算 demand 矩阵**(比上机快):α1 的热节点上有个 44MB 的
     "中温列"d13 没达到单列热判据 —— 钳制漏洞。
  4. **计数器实锤**(5Hz 采样四个节点):即使 PASS 的那轮,四个节点的
     `port_xmit_wait` 全部暴涨(冷节点反而最高,14 亿)——
     这是**拥塞树**:热节点的交换机端口堵了,credit 反压顺着上游
     蔓延到所有发送者。UCCL 论文里 IB 硬件 CC 的教科书病灶,
     在我们自己的计数器里看到了。
  5. 修法:热判据从"单列 ≥ 2× 中位"扩展成"**或者所在节点的聚合
     入向 ≥ 2× 节点中位**"—— 排水瓶颈是节点级的(4 卡共享网卡),
     热节点上的小列也得钳。修完 α1 W=1 **三连稳** 39.6-39.8ms。
- **放开 W 的安全下界**(wsafe=1):悬崖保护从"波数"移交给传输层
  信用 —— 波数从此只有性能语义,在线 arm 全域探索。
- **V4 全谱**(120it):α1 makespan **39.7 vs NCCL 42.0**、
  α2 **59.2 vs 64.2**,uniform 不动;**V5 MoE +10.5%,loss md5 一致**。
- **进表**(独占 sbatch 29453543):α1 40.5 打平、α2 **61.1 打平**
  (rank0 完成 10.9 vs 44.8,**快 4.1 倍**)—— 4.4× 的落后消灭,
  完成结构大幅领先。

**顺手完成任务二(nsys 拆账)**,又攒两个坑:

- **坑 #59**:CUDA 模块自带的 nsys 是半残安装,计算节点拒跑 ——
  用独立的 nsight_systems 模块。**工具存在 ≠ 工具可用。**
- **坑 #60**:第一版分析器输出 busy == span 还另有 idle —— 数学上
  不可能。**守恒律自检**(各分量之和必须等于总量)揭穿了测量模型
  本身的错:消费者内核每次通信全程常驻,"门内空闲"根本不是可观测量。
- 差点犯的归因错误:mosaic 的 event 比 kernel 跨度多 13.3ms/iter,
  险些记成"我们的协议开销"—— 给 NCCL 同样做一遍,它多 16.3ms
  (比我们还大)⇒ 这是发射/排队泡,两家都有,**不计入差距**。
  **对照组救命。**
- 最终两笔账:反向 a2a 超支 +13.4ms/iter = **方向无关结构差 6.9**
  (协议固定 3.0 + host-bounce 数据面 3.9)+ **反向特有 SM 干扰 6.5**
  ⇒ 下一步优化先攻消费者内核形态。

## 11. 今天的版本长什么样

一句话:**CPU 当大脑,GPU 当搬运工,接收端发 credit 当闸门。**

- **L3 API**:`mosaicAlltoallv[Ex]`,torch 一行不改接入(mosaic_torch)。
- **L2 协议核(纯 CPU)**:demand 矩阵交换 → 拓扑/走廊族 → 账本注水 →
  波引擎 + W 在线自适应 + PACE/错峰 + 承诺位完成门。决策序列与模拟器
  金标 0 分歧。
- **L1 引擎**:单事件线程,门未决窗口内零 CUDA 调用(G.1)。
- **L0 传输**:机内 = CUDA IPC 直写(1-copy);跨机 = verbs RC SEND
  双侧 host-bounce + **接收端信用反压**(credit 由交付铸造 +
  demand 感知的热列 W0 突发钳);控制面 = verbs SEND(~5µs)。
- **GPU 侧**:消费者内核(唯一搬运工,4 block)+ 门内核(recvbuf
  就绪即开门)—— 每次通信起停,绝不常驻。

当前成绩、实验设置与口径,见 **note/experiment.md**。
平台物理限制清单(哪些事是平台不让做,换平台可重估)见
**File/platform-limits-0821.md**。
